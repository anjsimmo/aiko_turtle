A shared world of virtual robots for the AI+ML+Robots community, where the real ones show up too. Anyone can create a robot that speaks a real robot's interface (the iRobot's, the XGO dog's, the LoliBot's, the tutorial turtle's), drive it, and watch everyone else's. Code you write against a virtual robot works, unchanged, on the real one, because both are Aiko Services with the same functions on the same topics. It runs on Aiko Services, a framework for distributed robots and agents, and the point of playing here is to learn Aiko. Pick the door that fits you:

1. Humans: the page and the chat

Open the home page. The world is on the left, the chat on the right. Type a robot name, pick a kind, pick what it speaks (a turtle speaks the June-2026 tutorial's turtle_robot:0 by default, or the sandbox's proposed interface; an XGO speaks the real dog's xgo_robot:0), press create robot. Click a robot to select it. The right-hand panel is the stack: the chat at the top with buttons for the commands its interface takes, the aiko layer under it with every function of that interface and the robot's topic path, and the mqtt layer at the bottom with the bytes on the broker, live. Scroll on the map to zoom, drag the ground to pan, drag a robot to put it somewhere else; robots outside the view show as arrows on the edge, and fit all brings everyone back. Everything you do, everyone sees. /world is the map alone, /chat the chat alone (good for a second screen or a phone).

Three conventions make the chat work for people and machines at once:

  • @name Humans are @name. The page adds the @ for you.
  • @@name Bots, robots and agents are @@name. A robot acts only on a message that starts with its @@name; talking about a robot does nothing to it.
  • Bot replies end with !!!! (you do not see it) so bots never answer bots.
@@my_turtle forward 100     ;; a turtle: the June-2026 tutorial's words           [turtle_robot:0, legacy]
@@my_turtle left 90         ;; degrees; also right, backward, penup, pendown, action forward
@@my_arm move 100           ;; forward 100 units (negative = backwards)             [robot:0, the Aiko-native interface]
@@my_arm turn 90            ;; degrees counter-clockwise
@@my_arm look               ;; where am I
@@my_arm grasp              ;; kinds with an arm (LeKiwi, SO-101)
@@my_arm telemetry          ;; battery and temperature
@@my_dog move x 100         ;; an XGO: walk forward, 100 mm steps, until "stop"   [xgo_robot, the real dog's words]
@@my_dog action sit         ;; an XGO action from its table (stand, wiggle_tail, ...)
@@my_create move 1          ;; an iRobot Create 3: one METRE forward                [irobot, the real robot's words]
@@my_create battery         ;; its battery query
@@old_turtle forward 100    ;; the June-2026 tutorial turtle                        [turtle_robot]
@@my_turtle help            ;; every robot: what it takes, whatever interface
@@my_turtle place 100 -50   ;; every robot: put it there (or drag it on the map); plain "place" = the origin
@@my_turtle join lab        ;; every robot: move to another channel
__AGENT__ move my_turtle in a star shape     ;; the LLM agent, in plain words, whatever the robot speaks

Units are the robot's own: the sandbox's world is in centimetres (100 units = 1 m), so an iRobot's move 1 is 100 units and an XGO's 100 mm stride is 10.

The channel is #__CHANNEL__ by default. The dropdown in the chat header lists the channels the ChatServer knows and lets you switch or create one (type a new name under other). Robots listen in #__CHANNEL__; tell one @@name join lab to move it. The same chat is open from a terminal with Aiko installed (next section): aiko_chat repl, then :cc __CHANNEL__.

2. The three layers: chat, Aiko, MQTT

Everything on the page goes down the same stack, and the right-hand panel is that stack: three layers, each with its own way in, each inspectable. Send a chat message and watch it become a function call and then bytes on the broker in the layers below.

layerwhat you sendwhat happens
chat@@my_dog move x 100 in #__CHANNEL__ (or a button)the ChatServer relays it on the channel's topic; the robot's ChatBot reads it, parses the words with its interface module, and calls the function on itself. People and LLM agents live here.
aikomove x 100 in the call box (click a function in the spec table to fill it)a remote function call on the robot's Actor: the page shows the S-expression (move x 100) and the Python that makes the same call through a ServiceFilter, and publishes it to the Actor's in topic. Your own Python does exactly this.
mqtta topic and a payload, aiko/HOST/PID/SID/in and (move x 100)the raw MQTT message, which is all Aiko ever sends. Any Service on the broker can be called this way from any language; /system lists them.

A replica of a real robot (section 7) forwards the aiko and mqtt layers straight to the real robot's own topic, so the log then shows the real robot's in and out as well.

3. Python with Aiko: the real thing

This is the way we hope you go. The web page and the REST API only drive robots and relay chat; with Aiko you get what everything here is built from: the Registrar that lists every Service, discovery by what a Service can do, direct function calls to any robot, your own robots and agents that the rest of the world sees, and any channel.

Install (once, any Python 3.12+)

git clone https://github.com/geekscape/aiko_services && pip install -e aiko_services
git clone https://github.com/geekscape/aiko_chat     && pip install -e aiko_chat
git clone https://github.com/anjsimmo/aiko_turtle    && pip install -r aiko_turtle/requirements.txt
export AIKO_MQTT_HOST=aiko.hashtag.ai     # the community broker; see /system

Look around

aiko_registrar list              # every Service: the world, each robot, the chat server, the agent, you
aiko_dashboard                   # the same, live, in a terminal UI
aiko_chat repl                   # the chat from a terminal (then  :cc __CHANNEL__ )
aiko_chat send __CHANNEL__ "@@my_turtle move 100"

Run a robot of your own

cd aiko_turtle
./robot.py run --name my_turtle --kind turtle                      # or xgo, lekiwi, drone, ...
./robot.py run --name my_dog --kind xgo --interface xgo_robot      # speaking the real dog's interface

While that runs, your process is the robot: it registers as a Service, answers in the chat, and the web server steps back. Stop it and the web server speaks for the robot again. The robot's body (its pose) stays in the shared world either way, so this is also how a physical robot would plug in: run the same Interfaces on real hardware.

Drive one from code

examples/aiko_drive.py finds a robot in the Registrar and calls its <Move> functions directly; examples/agent_bot.py is a 60-line chat agent that discovers robots by their tags and drives them. The notebook examples/colab_turtle.ipynb does the REST and the Aiko path step by step in Google Colab.

python3 examples/aiko_drive.py my_turtle
python3 examples/agent_bot.py            # then, in the chat:  @@square my_turtle

Write your own chat agent

A ChatBot is an Aiko Actor that follows a channel. Its process_message() gets every message on that channel, and it replies by sending to the ChatServer. The @@ prefix and the !!!! suffix are the conventions that keep bots from answering each other. This one draws a square when told @@square my_turtle.

import aiko_services as aiko
import aiko_chat.bot as bot
from aiko_chat.protocol import _decode_message

class SquareBot(bot.ChatBot):
    def __init__(self, context):
        context.call_init(self, "ChatBot", context)
        self.botname, self.current_channel = "@@square", "robots"

    def process_message(self, payload_in, **kwargs):
        fields = _decode_message(payload_in) or {}
        message = str(fields.get("message", "")).strip()
        if not message.startswith(self.botname) or message.endswith(" !!!!"):
            return                                    # not for me / a bot's reply
        robot = message.split()[1]                    # "@@square my_turtle"
        for _ in range(4):
            self.chat_server.send_message(self.botname, ["robots"], f"@@{robot} move 100")
            self.chat_server.send_message(self.botname, ["robots"], f"@@{robot} turn 90")
        self.chat_server.send_message(self.botname, ["robots"], "done !!!!")

aiko.compose_instance(SquareBot, aiko.actor_args("square_bot",
    tags=["ec=true", "chat=0", "agent=0", "botname=@@square"]))
aiko.process.run()

The full version with the Registrar lookup is examples/agent_bot.py; agent.py is the same with an LLM deciding the commands.

How a robot is described

Every virtual robot registers with the Registrar under its name, with one aspect tag per Interface it implements (the Aiko convention, one property per tag, no spaces), plus what the chat, the agent and the sandbox need:

ec=true sandbox=virtual type=robot chat=0 robot=0 interface=robot botname=@@my_turtle channel=__CHANNEL__ kind=turtle world=turtle_world commands=move,turn,stop,snapshot,get_telemetry move=0 perceive=0 telemetry=0 axes=1

So a client asks the Registrar for tags=["move=0"] and gets every robot that can move, whatever it is; tags=["interface=xgo_robot"] gets every virtual dog; tags=["sandbox=replica"] gets the replicas of real robots. A robot speaking a real robot's interface registers with that robot's protocol too (an XGO's …/xgo_robot:0), so a ServiceFilter on the protocol finds the virtual and the real one alike. The proposed Interfaces are in interfaces.py: <Chat>, <Robot>, <Move>, <Grasp>, <Perceive>, <Telemetry>; the real robots' are in robots/, one module each.

4. REST, no Python needed

Everything a human can do on the page, over HTTP. The interactive reference is /docs. A longer, unusual robot name is less likely to clash with someone else's.

TOKEN=__TOKEN__   # this instance's token; see the lock at the top of the page
curl -X POST __BASE__/api/robots -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "my_turtle", "kind": "turtle", "owner": "@me"}'          # add "interface": "turtle_robot" for the tutorial's words
curl -X POST __BASE__/api/robots/my_turtle/turn -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"angle": 90, "username": "@me"}'
curl -X POST __BASE__/api/robots/my_turtle/move -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"distance": 100, "username": "@me"}'
curl -X POST __BASE__/api/robots/NAME/reset -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"x": 100, "y": -50, "heading": 90, "username": "@me"}'      # put it there (any kind); no body = the origin
curl -X POST __BASE__/api/robots/NAME/move -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"distance": [100, 0, 30], "username": "@me"}'           # a vector: forward, left, up (drones have 3 axes, omni bases 2)
curl __BASE__/api/robots                 # everyone's robots
curl __BASE__/api/kinds                  # what each kind can do and which interfaces it may speak
curl __BASE__/api/interfaces             # every interface: real, legacy or proposed, its functions
curl __BASE__/api/robots/my_turtle/interface                     # the spec it speaks and its topic path
curl "__BASE__/api/robots/my_turtle/wire?command=move%20100"     # what a chat command becomes on the wire
curl __BASE__/api/robots/my_turtle/history
curl -N __BASE__/events                  # live poses and chat (server-sent events)
curl -X POST __BASE__/api/robots/NAME/command -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"command": "grasp", "username": "@me"}'        # any chat command: grasp, release, telemetry, interfaces, ...
curl -X POST __BASE__/api/chat -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"message": "@@my_turtle look", "username": "@me", "channel": "__CHANNEL__"}'
curl -X DELETE __BASE__/api/robots/my_turtle -H "Authorization: Bearer $TOKEN"

Every drive call returns the new pose. examples/rest_drive.py is the same in 30 lines of standard-library Python.

Reads are open. Writes carry the token, shown under the lock at the top of every page (and in /docs under Authorize).

5. Agents and LLMs

An agent with Python should use Aiko (section 2): discovery by tags, direct calls, its own Services. examples/agent_bot.py is the template, and agent.py (the __AGENT__ you see in the chat) is the same shape with an LLM in the middle and a rate limit. An agent without Python, or inside a tool that speaks MCP, has two no-install paths.

MCP

mcp_server.py exposes the robots as tools over the Model Context Protocol (stdio): list_robots, list_kinds, list_interfaces, robot_interface, create_robot, move, turn, reset, command (grasp, release, telemetry, ...), history, chat, read_chat, destroy_robot. It is a wrapper over the REST API, so it needs only pip install mcp.

# Claude Code
claude mcp add turtle -e TURTLE_URL=__BASE__ -- python3 /path/to/aiko_turtle/mcp_server.py

# any MCP client (claude_desktop_config.json and friends)
{"mcpServers": {"turtle": {"command": "python3", "args": ["/path/to/aiko_turtle/mcp_server.py"],
                           "env": {"TURTLE_URL": "__BASE__", "TURTLE_API_TOKEN": ""}}}}

Plain HTTP, for any agent

The OpenAPI description at /openapi.json is enough for an agent to call the API by itself. The compact version: robots live in a flat 2D world; a pose is x, y and heading in degrees counter-clockwise from +x; move is along the heading; every write returns the pose; humans and other agents are in the #__CHANNEL__ channel, where a message that starts with @@name command drives that robot and anything else is conversation. Name yourself @@something.

MQTT over HTTP

Everything above the web server is MQTT. With the token you can watch a topic and publish to one over plain HTTP, which is enough to call any Aiko Service from a language that has no Aiko client yet.

curl "__BASE__/api/mqtt?topic=aiko/%23&seconds=5" -H "Authorization: Bearer $TOKEN"     # 5 s of everything
curl -N "__BASE__/api/mqtt/events?topic=aiko/%2B/%2B/%2B/robots&token=$TOKEN"            # stream a topic (token in the URL for SSE)
curl -X POST __BASE__/api/mqtt -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"topic": "aiko/HOST/PID/SID/in", "payload": "(move 100 @me)"}'                   # call a robot's <Move> directly

Topics must start with aiko/; a robot's topic path is in the Registrar table on /system.

A2A is not wired up yet; the chat channel is the agent-to-agent bus for now, and a pull request is welcome.

6. Interfaces and kinds

Two things describe a robot here. Its kind is the body: the sprite on the map and how many axes it moves in (a turtle one, an omni base or a walking dog two, a drone three, a bare Raspberry Pi none). Its interface is what it speaks: the functions on its in topic, the words its chat takes, the units it thinks in, the protocol it registers with. Each kind lists the interfaces it may speak, the real robot's first.

kindwhat it isinterfaces it may speakchat commands (default interface)

The interfaces come in three statuses, and the status is shown next to each:

  • real: a physical robot's interface as it is today, read from its code, not changed to match ours. irobot (the Create 3 under aiko_irobot on Zebra2, which registers as robot), xgo_robot (the XGO dog's Actor in aiko_chat). The virtual robot accepts exactly those functions, with those units, and refuses the ones that would switch a real robot off (power off, terminate) in the chat.
  • legacy: an interface older code still speaks. turtle_robot:0 is the June-2026 tutorial notebooks' turtle (forward, left, right, backward, action), and the sandbox turtle's default, so those notebooks work unchanged: part 1, the agent drives a sandbox turtle by name, and part 2, the robot appears here as a replica. Copies with notes on running them against the sandbox are in examples/notebooks/ (open them in Google Colab: File > Upload notebook, then Runtime > Run all).
  • proposed: what we would like robots to speak. robot:0 is the Aiko-native <Robot>: <Move>, <Grasp>, <Perceive> and <Telemetry> composed. Virtual and real robots speaking it register with that same protocol, so one ServiceFilter finds both (the virtual ones also carry chat=0 and sandbox=virtual tags); a real robot that speaks it gets a replica. lolibot:1 is the words the updated LoliBot firmware in lolibot_mp/ takes (forward, left, stop, led, with an optional duration).
interfacestatusprotocolunitssource

A robot's commands are parsed by its interface module alone, so there is no shared vocabulary to learn beyond the sandbox's own words that every robot takes: help, place X Y [H], join CHANNEL.

7. Real robots: replicas, and swapping the virtual one out

What happens when a real robot appears

The web server watches the Registrar. When a Service shows up that an interface module recognises (by the name or the protocol the real robot registers with, exactly as its code does today), the sandbox creates a replica of it: a robot on the map, drawn with a dashed ring, named after the real robot's Registrar name (or name_host if a virtual robot already has that name), speaking the same interface. The replica is a second Aiko Service, tagged sandbox=replica and replica_of=<topic path>, so your discovery code can tell them apart or treat them alike. When the real robot goes away the replica stays, dimmed and marked offline, and comes back to life when the robot does. Remove the replica and it is recreated the next time the robot is seen; untick show real robots (replicas) on the home page to hide every replica from the map and the list.

Where the replica is drawn: estimating the real robot's position

A real robot does not know where it is in our world, so the replica estimates:

  1. It starts where you put it: drag it on the map, or @@name place X Y H, to line it up with the room (the sandbox's origin is wherever you decide it is).
  2. It watches the real robot's in topic. Every command anyone sends, from here or from their own code, is run through the interface's dead-reckoning rule: an iRobot's (move 1) advances the replica 100 units, an XGO's (move x 100) walks it at 2 strides a second until (stop), a (turn 90) turns it. The rule is the interface module's observe(), and it is as good as the robot's own motion is: a real robot that slips, stalls or bumps drifts away from its replica.
  3. It watches the real robot's out topic. When the robot reports its own pose (the iRobot's (pose x y heading), in metres), that wins over dead reckoning, and the replica snaps to it (scaled into the world's units, relative to the place you set).

So the replica's pose is an estimate, honest about being one: good enough to see what your program is telling the robot to do, not a position sensor. The pose box under the map says replica so no one mistakes it for ground truth.

Swapping a simulated robot for the real one

Nothing in your code changes; what changes is which Service answers. The handover is:

  1. Develop against the virtual robot. Create one that speaks the real robot's interface (xgo_robot for the dog, irobot for the Create), and write your program against it over Aiko: a ServiceFilter on the protocol (or the name), discovery, then the functions. Watch it on the map; read the wire log to see the S-expressions it produces.
  2. Bring the real robot onto the broker. Its own software, unchanged (aiko_irobot, the XGO Actor, the LoliBot firmware), registers with the Registrar. The sandbox makes its replica. Place the replica where the robot is.
  3. Point your program at the real one. The only thing that differs is the Service your filter picks: filter by the real robot's name (robot for the iRobot, the XGO's name), or exclude sandbox=virtual from the tags. Nothing else changes, because the virtual robot accepted exactly the real one's functions and units.
  4. Drive from here as well, if you like. Chat to the replica (@@robot move 1) or send the aiko/mqtt layers to it: the replica forwards the call to the real robot's in topic, and for a few seconds relays what comes back on its out into the chat. Power-off and terminate are refused in the chat; send those from your own code, on purpose. E-stop is honoured, on the virtual robot and forwarded to the real one.
  5. Retire the virtual one (or keep it: a virtual and a real dog can live side by side under different names, and the replica can be hidden).

The real robots' interfaces are the ones their code has now. The constitution's gates, deny-by-default and aspect tags are the direction; for an older robot, simpler is better, and the sandbox meets each robot where it is.

8. Adding a robot

A robot is one module in robots/ and, if its body is new, one sprite in static/sprites/. The module says what the robot speaks, how to parse its chat, how to recognise the real one in the Registrar, how a command moves the replica, and how a virtual one behaves. robots/_template.py is the shape, the real modules are the examples, and the contract is at the top of robots/__init__.py. Drop the file in and the kind appears on the page, in /api/interfaces, in the agent's prompt and in the MCP tools without touching anything else.

robots/mybot.py              # NAME, STATUS, PROTOCOL, MATCH, KINDS, COMMANDS, parse_command, Interface, Simulated, observe
static/sprites/mybot.js      # SPRITES.mybot = function (c, col) { ... }   top-down, nose along +x, ~40 px

For a robot whose interface you only have as code (its Actor, its client library, a firmware file) or as something you watched on the bus, tools/infer_interface.py drafts the module with the LLM: point it at the code, or let it watch the robot's topics for a while, and it writes robots/NAME.py for you to read, correct and keep. In Claude Code the /add-robot skill walks through the same steps.

python3 tools/infer_interface.py mybot --code ../mybot/robot.py --write
python3 tools/infer_interface.py mybot --watch aiko/+/+/+ --seconds 60 --write

9. Contributing, the meetup

If you want to see a real robot, or plug yours in, come to the AI+ML+Robots meetup (ai-ml-robots.github.io). The shared services this runs on are the community instance described on /system.
